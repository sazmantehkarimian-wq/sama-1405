# MD بهره‌برداران — SAMA

**پروژه:** سامانه املاک سازمان فرهنگی هنری شهرداری تهران (SAMA)  
**حوزه:** بهره‌برداران  
**وضعیت:** `FROZEN`

---

# 1. هدف و جایگاه «بهره‌برداران» در SAMA

ماژول «بهره‌برداران» برای نگهداری و مدیریت هویت، اطلاعات تماس، فضاهای جاری، سوابق فضاها، قراردادها، اسناد، مکاتبات و تاریخچه ارتباط هر بهره‌بردار با فضاهای تجاری طراحی می‌شود.

`Beneficiary` یک موجودیت مستقل است و زیرمجموعه قرارداد یا فضای تجاری محسوب نمی‌شود.

اصل طراحی:

> **فهرست جامع → پرونده جامع هر بهره‌بردار**

---

# 2. شناسه یکتای بهره‌بردار

برای هر بهره‌بردار یک کد سیستمی یکتا ایجاد می‌شود.

نمونه:

```text
BEN-000001
```

## 2.1 قواعد کد بهره‌بردار

- به‌صورت سیستمی ایجاد می‌شود.
- یکتا است.
- غیرقابل تغییر است.
- برای شناسایی پرونده استفاده می‌شود.
- شماره ملی یا شناسه ملی جایگزین این کد نمی‌شود.
- حذف یا تغییر اطلاعات هویتی باعث تغییر کد نمی‌شود.

# 3. صفحه اصلی «بهره‌برداران»

## 3.1 ستون‌های اصلی فهرست

| فیلد | توضیح |
|---|---|
| کد بهره‌بردار | شناسه ثابت پرونده |
| نام / عنوان بهره‌بردار | شخص حقیقی یا شخصیت حقوقی |
| نوع بهره‌بردار | حقیقی / حقوقی |
| کد ملی / شناسه ملی | در صورت ثبت |
| فضای جاری | کد فضا یا تعداد فضاهای جاری |
| نام فضای جاری | برای تشخیص سریع |
| منطقه | منطقه فضای جاری |
| قرارداد جاری | شماره قرارداد یا «فاقد قرارداد» |
| تاریخ پایان قرارداد | در صورت وجود |
| وضعیت ارتباط | دارای فضای جاری / فاقد فضای جاری |
| وضعیت پرونده | کامل / نیازمند تکمیل / نیازمند بررسی |
| اقدام | مشاهده پرونده |

اگر بهره‌بردار بیش از یک فضای جاری داشته باشد، فهرست نباید چند نام را در یک سلول شلوغ کند.

نمونه نمایش:

```text
3 فضای جاری — مشاهده
```

# 9. جلوگیری از ثبت بهره‌بردار تکراری

کنترل اصلی Duplicate بر اساس شناسه هویتی انجام می‌شود.

## 9.1 شخص حقیقی

کنترل اصلی:

```text
کد ملی
```

## 9.2 شخص حقوقی

کنترل اصلی:

```text
شناسه ملی
```

اگر پرونده‌ای با همان شناسه وجود داشته باشد، SAMA باید هشدار دهد و پرونده موجود را پیشنهاد کند.

نمونه:

```text
پرونده‌ای با این شناسه قبلاً ثبت شده است.
```

شباهت نام به‌تنهایی مانع ثبت نیست، زیرا امکان وجود افراد هم‌نام وجود دارد.

اگر کد ملی یا شناسه ملی هنوز در دسترس نباشد، ثبت پرونده ناقص مجاز است، اما وضعیت پرونده باید «نیازمند تکمیل هویت» یا معادل مصوب آن را نشان دهد.

# 10. رابطه بهره‌بردار با فضای تجاری

بهره‌بردار می‌تواند در طول زمان با یک یا چند فضای تجاری ارتباط داشته باشد.

رابطه بهره‌بردار و فضا باید تاریخچه مستقل داشته باشد.

برای هر ارتباط:

- کد فضا
- نام فضا
- تاریخ شروع
- تاریخ پایان
- وضعیت ارتباط
- قرارداد مرتبط، در صورت وجود
- مبنای ارتباط
- علت خاتمه
- توضیحات
- ثبت‌کننده
- تاریخ ثبت

نگهداری می‌شود.

---

# 11. فضاهای جاری بهره‌بردار

در پرونده بهره‌بردار، فضاهای جاری باید به‌صورت واضح نمایش داده شوند.

| فیلد | توضیح |
|---|---|
| کد فضا | شناسه فضای تجاری |
| نام فضا | عنوان |
| منطقه | منطقه فضا |
| وضعیت فضا | فعال / از دور خارج‌شده |
| قرارداد | شماره قرارداد جاری، در صورت وجود |
| تاریخ شروع | شروع ارتباط |
| تاریخ پایان | در صورت وجود |
| اقدام | مشاهده پرونده فضا |

کلیک روی کد یا نام فضا باید کاربر را به پرونده همان فضای تجاری ببرد.

---

# 12. سابقه فضاها

فضاهای قبلی بهره‌بردار حذف نمی‌شوند.

نمونه:

```text
کد 188 — 1401 تا 1402
کد 309 — 1402 تا 1404
کد 378 — جاری
```

سامانه باید امکان مشاهده کامل تاریخچه فضاهای یک بهره‌بردار را فراهم کند.

---

# 13. قراردادهای بهره‌بردار

قرارداد یک Entity مستقل است.

در پرونده بهره‌بردار فقط نمای مرتبط قراردادها نمایش داده می‌شود.

## 13.1 اطلاعات نمایش

- شماره قرارداد
- کد فضا
- نام فضا
- تاریخ شروع
- تاریخ پایان
- مبلغ
- وضعیت
- مشاهده پرونده قرارداد

## 13.2 قواعد

- هر قرارداد فقط یک بهره‌بردار دارد.
- یک بهره‌بردار می‌تواند در طول زمان چند قرارداد داشته باشد.
- قرارداد تاریخی حذف نمی‌شود.
- حذف یا اصلاح اطلاعات بهره‌بردار نباید سوابق تاریخی قرارداد را از بین ببرد.
- اطلاعات قرارداد در پرونده بهره‌بردار دوباره ذخیره نمی‌شوند و از منبع اصلی Contract خوانده می‌شوند.

---

# 14. بهره‌بردار بدون قرارداد

وجود بهره‌بردار و وجود قرارداد دو مفهوم مستقل هستند.

یک فضا می‌تواند:

- بهره‌بردار داشته باشد و قرارداد جاری نداشته باشد.
- فاقد بهره‌بردار باشد.
- قرارداد تاریخی داشته باشد ولی بهره‌بردار جاری نداشته باشد.

در صورت وجود بهره‌بردار بدون قرارداد، سامانه باید صریحاً نمایش دهد:

```text
بهره‌بردار فعلی: ...
قرارداد جاری: فاقد قرارداد
```

این وضعیت باید در گزارش‌گیری مستقل قابل استخراج باشد.

---

# 15. تغییر بهره‌بردار

تغییر بهره‌بردار یک ویرایش ساده روی مقدار قبلی نیست.

در صورت تغییر بهره‌بردار یک فضای تجاری:

1. ارتباط قبلی خاتمه داده می‌شود.
2. تاریخ پایان ثبت می‌شود.
3. علت خاتمه، در صورت نیاز، ثبت می‌شود.
4. ارتباط جدید ایجاد می‌شود.
5. تاریخ شروع ارتباط جدید ثبت می‌شود.
6. کاربر ثبت‌کننده و زمان عملیات در Audit ذخیره می‌شوند.

سابقه قبلی overwrite نمی‌شود.

---

# 16. اسناد و مدارک بهره‌بردار

این بخش فقط برای مدارکی است که متعلق به خود شخص یا شخصیت حقوقی است.

نمونه:

- مدرک هویتی
- مدارک ثبت شخصیت حقوقی
- معرفی‌نامه
- وکالت‌نامه
- سایر مدارک مرتبط با هویت یا نمایندگی

## 16.1 فایل

وجود فایل الزامی نیست.

ثبت اطلاعات مدرک بدون فایل مجاز است.

در صورت نبود فایل، پرونده قابل استفاده باقی می‌ماند و فقط وضعیت تکمیل مشخص می‌شود.

مکاتباتی که موضوع اصلی آنها خود بهره‌بردار است می‌توانند به پرونده او متصل شوند.

فیلدهای پایه:

- شماره
- تاریخ
- موضوع

- گیرنده
- وضعیت پیگیری
- قرارداد مرتبط، در صورت وجود

- فایل
- توضیحات

- تاریخ ثبت

اگر مکاتبه متعلق به یک قرارداد یا فرآیند تخصصی باشد، اصل سند در ماژول اصلی همان فرآیند مدیریت می‌شود و در پرونده بهره‌بردار فقط ارتباط آن نمایش داده می‌شود.

# 19. وضعیت تکمیل پرونده

وضعیت تکمیل توسط سیستم محاسبه می‌شود.

مقادیر اصلی:

- کامل
- نیازمند تکمیل
- نیازمند بررسی

نمونه:

```text
نیازمند تکمیل:
- کد ملی ثبت نشده
- شماره تماس موجود نیست
```

Completeness برای کنترل کیفیت داده است و نباید بدون دلیل مانع استفاده از پرونده شود.

نبود شماره تماس یا فایل مدرک به‌تنهایی نباید پرونده را غیرقابل استفاده کند.

# 21. اطلاعات مالی

پرونده بهره‌بردار به دفتر مالی مستقل تبدیل نمی‌شود.

اطلاعات مالی قرارداد از ماژول قراردادها خوانده می‌شود.

اگر در آینده ماژول مستقل مطالبات، بدهی یا حساب بهره‌بردار طراحی شود، در پرونده بهره‌بردار فقط خلاصه و ارتباط آن نمایش داده می‌شود.

داده مالی نباید در چند محل جداگانه تکرار شود.

# 24. اصول معماری تثبیت‌شده

1. `Beneficiary` یک موجودیت مستقل است.
2. هر بهره‌بردار یک کد یکتای سیستمی دارد.
3. کد بهره‌بردار غیرقابل تغییر است.
4. حقیقی و حقوقی ساختار هویتی متناسب با خود دارند.
5. کد ملی و شناسه ملی کنترل اصلی Duplicate هستند.
6. شباهت نام به‌تنهایی مانع ثبت نیست.
7. یک بهره‌بردار می‌تواند در طول زمان چند فضا داشته باشد.
8. یک بهره‌بردار می‌تواند در طول زمان چند قرارداد داشته باشد.
9. هر قرارداد فقط یک بهره‌بردار دارد.
10. بهره‌بردار بدون قرارداد قابل ثبت و گزارش است.
11. «فاقد بهره‌بردار» با «فاقد قرارداد» یکی نیست.
12. سابقه فضاها حذف یا overwrite نمی‌شود.
13. سابقه قراردادها حذف یا overwrite نمی‌شود.
14. فضا و قرارداد از منبع اصلی خود خوانده می‌شوند و داخل Beneficiary دوباره ذخیره نمی‌شوند.
15. تغییر بهره‌بردار یک Event تاریخی است.
16. فایل اسناد بهره‌بردار اجباری نیست.
17. اطلاعات مالی تخصصی در ماژول مالی/قرارداد باقی می‌ماند.
18. Audit Trail برای تغییرات مهم الزامی است.
19. وضعیت تکمیل پرونده توسط سیستم محاسبه می‌شود.
20. هیچ اطلاعات نامطمئنی برای کامل نشان دادن پرونده حدس زده نمی‌شود.
